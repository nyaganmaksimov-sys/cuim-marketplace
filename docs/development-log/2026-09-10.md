## 09.09.2026 — двусторонняя связь A4PRINT KASSA ↔ HUB-заказы

**Статус:** APPLIED / BACKEND  
**Подсистема:** POS / HUB / orders / payments / cash / customers

Что изменено:

- `pos_sales` теперь содержит `order_id` и может быть связан с существующим HUB-заказом;
- `payments` получил связь `pos_sale_id`, что позволяет однозначно сопоставлять оплату и кассовую продажу;
- добавлен `record_pos_sale_v2(...)`: кассовая продажа может оплатить переданный HUB-заказ либо, если `p_order_id` отсутствует, автоматически создать завершённый заказ из состава чека;
- при автоматическом создании заказа позиции формируются из `p_items`, источник фиксируется как `KASSA`, а заказ связывается с оператором/клиентом;
- для кассовой продажи создаётся/обновляется платёж `INCOME / PAID` и сохраняется прежняя синхронизация денежной операции в `cash_transactions`;
- повторный вызов по той же продаже остаётся идемпотентным: используется существующий unique `(organization_id, moysklad_sale_id)`, а для платежа создан уникальный partial index по `pos_sale_id`.

Миграции:

- `20260909215603` — `pos_order_bidirectional_link`;
- `20260909215838` — `pos_hub_order_checkout_api`;
- `20260909220221` — `fix_pos_created_order_items_catalog_reference`.

Важные технические решения:

- POS-чек и HUB-заказ больше не являются параллельными независимыми сущностями: связь хранится непосредственно в БД;
- один POS sale соответствует не более чем одному платежу через `payments_pos_sale_id_uidx`;
- если продажа создаёт заказ автоматически, `order_items.product_id/service_id` не заполняются недостоверными внешними идентификаторами; исходная информация чека сохраняется в `parameters`;
- сервер самостоятельно создаёт номер нового заказа под advisory lock и не доверяет номеру из браузера;
- доступ `record_pos_sale_v2(...)` ограничивается внутренней проверкой ролей `ADMIN`/`POS_OPERATOR` и действующего HUB-пользователя.

Проверка:

- подтверждены `pos_sales.order_id -> orders(id) ON DELETE SET NULL` и `payments.pos_sale_id -> pos_sales(id) ON DELETE SET NULL`;
- подтверждён индекс `payments_pos_sale_id_uidx` с уникальностью по непустому `pos_sale_id`;
- текущая production-версия `record_pos_sale_v2(...)` возвращает `sale_id`, `order_id`, `payment_id` и содержит проверки `POS_CONTEXT_NOT_FOUND` / `POS_ACCESS_REQUIRED`;
- legacy `record_pos_sale(...)` сохранён для обратной совместимости.

## 09–10.09.2026 — POS API для выбора и оплаты существующих HUB-заказов

**Статус:** APPLIED / BACKEND  
**Подсистема:** POS / orders / customers / payments / authz / RPC

Что изменено:

- добавлен `get_pos_hub_orders(query, limit)` для поиска незакрытых HUB-заказов с расчётом уже оплаченной суммы и остатка долга;
- добавлен `get_pos_hub_order(order_id)` для получения карточки заказа с клиентом, составом позиций, общей суммой и фактически оплаченной суммой;
- выборка скрывает отменённые заказы и возвращает только заказы с положительным остатком долга;
- поиск работает по номеру заказа, имени/названию клиента и телефону;
- обе функции выполняют внутреннюю проверку `ADMIN` или `POS_OPERATOR`.

Важные технические решения:

- остаток к оплате вычисляется из реальных `payments`: оплаченный `INCOME` увеличивает оплату, `REFUND` уменьшает её;
- POS не должен доверять сумме долга из UI — сервер возвращает её из текущего состояния HUB;
- лимит выдачи принудительно ограничен максимум 100 строками.

Проверка:

- обе RPC фактически присутствуют в production как `SECURITY DEFINER`;
- в определениях подтверждена проверка `has_role('ADMIN') or has_role('POS_OPERATOR')`;
- Security Advisor отдельно отмечает, что `get_pos_hub_orders(...)`, `get_pos_hub_order(...)` и `record_pos_sale_v2(...)` всё ещё имеют `anon EXECUTE=true`. Из-за встроенных проверок анонимный пользователь не проходит авторизацию, но сами EXECUTE-grants являются лишней поверхностью и требуют отдельного hardening-прохода.

Security follow-up:

- отозвать `EXECUTE` у `anon` для `get_pos_hub_orders(...)`, `get_pos_hub_order(...)`, `record_pos_sale_v2(...)` без изменения поведения для `authenticated` POS-пользователей;
- после hardening повторно прогнать Supabase Security Advisor: https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable

Коммиты продукта: новых нет.

## 10.09.2026 — SaaS billing control center

**Статус:** APPLIED / BACKEND FOUNDATION  
**Подсистема:** SaaS / billing / plans / subscriptions / payments / promo / gateway settings

Что изменено:

- создан серверный контур коммерциализации ЦУИМ: `saas_plans`, `saas_subscriptions`, `saas_promo_codes`, `saas_payment_transactions`, `saas_gateway_settings`, `saas_commerce_settings`;
- заведены четыре стартовых тарифа: `FREE`, `BUSINESS`, `PRO`, `NETWORK`;
- тарифы поддерживают месячную/годовую цену, лимиты сотрудников, точек и заказов, набор features и признак featured;
- `saas_subscriptions` хранит тариф, статус, период биллинга, trial, период действия, фиксацию цены и внешние идентификаторы платёжного шлюза;
- `saas_payment_transactions` отделяет SaaS-платежи от операционной кассы HUB и хранит provider/payment id/payload/paid_at;
- `saas_gateway_settings` предусматривает подключение платёжного провайдера, test mode, публичную конфигурацию и отдельные зашифрованные поля для секретов/webhook secret;
- `saas_commerce_settings` задаёт коммерческие параметры лендинга и trial: 14 дней, годовая скидка 20%, early-adopter режим на 12 месяцев, переход на FREE после trial.

Миграция:

- `20260910055832` — `saas_billing_control_center`.

Текущая стартовая тарифная сетка в production:

- `FREE` — 0 ₽, 1 сотрудник, 1 точка, до 50 заказов/месяц;
- `BUSINESS` — 1 490 ₽/мес., 14 300 ₽/год, 5 сотрудников, 1 точка, featured;
- `PRO` — 2 990 ₽/мес., 28 700 ₽/год, 15 сотрудников, до 3 точек;
- `NETWORK` — 5 990 ₽/мес., 57 500 ₽/год, без лимита сотрудников, до 5 точек.

Важные технические решения:

- платёжный шлюз по умолчанию `manual`, `enabled=false`, `test_mode=true`: реальный эквайринг ещё не включён;
- secret-конфигурация и webhook secret отделены от публичного JSON-конфига;
- промокоды заведены как отдельная сущность с типом/значением скидки, лимитом использований, окном действия и областью применимости;
- коммерческие тексты и параметры trial вынесены из фронтенда в БД, чтобы тарифы/оффер можно было менять без пересборки UI.

Проверка и безопасность:

- все шесть SaaS-таблиц фактически присутствуют в production и имеют `RLS=true`;
- на момент проверки для этих таблиц нет RLS policies; поэтому Data API фактически работает в deny-all режиме, хотя стандартные `SELECT` grants на `anon/authenticated` ещё присутствуют;
- свежий Security Advisor отмечает все шесть SaaS-таблиц как `RLS Enabled No Policy`; это допустимо для закрытого серверного фундамента, но grants лучше явно минимизировать до появления контролируемых SaaS RPC/policies;
- в `saas_gateway_settings` провайдер сейчас `manual`, шлюз выключен, test mode включён, секретная конфигурация и webhook secret отсутствуют — production-списаний эта миграция сама по себе не включает;
- промокоды пока не созданы (`saas_promo_codes` пуст).

Security follow-up:

- до подключения UI/эквайринга определить явную модель доступа к тарифам и подпискам: публичное чтение только безопасных полей тарифов через RPC/view, подписки и платежи — только owner/admin/server;
- явно отозвать ненужные прямые grants с `saas_gateway_settings`, `saas_payment_transactions`, `saas_subscriptions` и других внутренних SaaS-таблиц;
- leaked-password protection в Supabase Auth по-прежнему отключён: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection

Коммиты продукта: новых нет.
