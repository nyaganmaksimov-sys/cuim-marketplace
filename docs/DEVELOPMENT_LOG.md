## Как ведётся журнал

Этот файл — обзорный реестр развития продукта. Полным неизменяемым техническим источником истины остаётся Git. Здесь содержательные коммиты объединяются по пользовательскому результату: функции, интерфейс, БД, RPC, RLS, Storage, Edge Functions, безопасность, миграции и тесты.

Правила:

- после завершённого этапа добавляется запись;
- указываются дата, подсистема, результат, техническое решение, проверка и SHA;
- изменения Supabase фиксируются вместе с относящимся к ним продуктовым этапом;
- секреты, платёжные ключи, токены и персональные данные не записываются;
- мелкие коммиты могут объединяться в один этап;
- ежедневный аудит проверяет пропущенные изменения.

# 8. Переход к запуску в Москве

## Решение о рынке

ЦУИМ развивается как масштабируемая городская платформа. Первым крупным рынком выбрана **Москва**, запуск — постепенный. Геоядро проектируется так, чтобы впоследствии добавлять другие города без переделки основы.

**Ключевая точка:** `3fbef9cbdb17f13f45063b923b0ab08ec1b62471`.

- Иерархия: страна → регион → город → административный округ → район → метро/микрорайон.
- Старые текстовые поля временно сохранены для совместимости.

# 9. Безопасность и технический долг

Принципы новой разработки:

- публичные API должны отдавать только данные витрины;
- управляющие операции требуют авторизации и проверки владельца/роли;
- приватные CRM/платёжные сведения не выдаются `anon`;
- для новых `SECURITY DEFINER` фиксируется `search_path` и явно настраивается EXECUTE;
- после DDL выполняется аудит прав и Supabase Advisor;
- геомиграция остаётся совместимой со старыми данными до завершения миграции продавцов.

## 03.09.2026 — аудит Supabase Advisor

После новых geo-write RPC запущен Security Advisor.

**Новые функции:** anon-доступ к двум новым управляющим geo-функциям закрыт и отдельно проверен.

**Обнаруженный существующий технический долг:** Advisor показал значительное количество старых `SECURITY DEFINER` RPC, которым исторически был выдан EXECUTE для `anon` или всех `authenticated`, а также две security-definer view, таблицы с RLS без политик и отключённую leaked-password protection.

## 03.09.2026 — первый системный Supabase Security Hardening

**Статус:** DONE  
**Подсистема:** database / authz / RLS / RPC / Storage

Миграции:

- `security_harden_function_acl_and_internal_views`;
- `security_harden_helper_function_search_paths`;
- `security_revoke_direct_access_to_deny_all_internal_tables`;
- `security_harden_dormant_storage_uploads`;
- `security_minimize_anonymous_table_writes`;
- `security_hide_internal_marketplace_columns`.

Что изменено:

- с внутренних и пользовательских `SECURITY DEFINER` RPC снят лишний `EXECUTE` для `anon`; публичными оставлены только витринные/счётчиковые сценарии, где анонимный вызов является частью продукта;
- `marketplace_open_requests_v2` закрыт от анонимного вызова и теперь проверяет наличие действующего профиля партнёра;
- `set_marketplace_request_media` выведен из браузерного API и оставлен только для доверенного сервисного вызова;
- trigger-функции синхронизации и `handle_new_auth_user` больше не исполняются клиентскими ролями;
- helper-функции ролей/партнёров переведены на фиксированный пустой `search_path` с явными schema-qualified ссылками;
- `inventory_balances` и `payment_totals` переведены в `security_invoker=true`, а прямой `anon SELECT` закрыт;
- для внутренних deny-all таблиц убраны прямые GRANT клиентским ролям; проверка показала **0** прямых прав `anon`/`authenticated` на набор из 22 таких таблиц;
- дополнительно минимизированы старые anonymous table writes и скрыты внутренние marketplace-колонки от прямого Data API.

Проверка:

- `checkout_marketplace_cart_v2`: `anon=false`, `authenticated=true`;
- `courier_open_offers`: `anon=false`, `authenticated=true`;
- `marketplace_admin_reclassify_products`: `anon=false`, `authenticated=true`;
