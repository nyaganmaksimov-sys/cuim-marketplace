## Как ведётся журнал

Этот файл является обзорным реестром развития продукта. Низкоуровневым неизменяемым источником истины для каждого изменения файлов остаётся история Git. В журнал попадают все содержательные изменения продукта и инфраструктуры: новые функции, изменения интерфейса, схемы БД, RPC, RLS, Edge Functions, интеграции, исправления, безопасность, миграции, тесты и важные архитектурные решения.

Правила ведения:

- после завершённого этапа или исправления добавляется запись в этот файл;
- запись содержит дату, подсистему, что изменено, техническое решение, проверку и SHA коммита/коммитов;
- изменения Supabase фиксируются отдельно от фронтенда, даже если относятся к одной функции;
- секреты, ключи оплаты, токены и персональные данные в журнал не записываются;
- если несколько мелких коммитов относятся к одному пользовательскому результату, они объединяются в одну содержательную запись, а Git остаётся полным механическим журналом;
- поле **«Последняя учтённая точка»** обновляется после каждого пополнения;
- ежедневный аудит проверяет, не появились ли коммиты, пропущенные журналом.

# 8. Переход к запуску в Москве

## Решение о рынке

Принято продуктовое решение: ЦУИМ развивается не как сервис одного небольшого города, а как масштабируемая городская платформа. Первым крупным рынком становится **Москва** с постепенным запуском.

Архитектура географии проектируется так, чтобы впоследствии без переделки ядра подключать другие города.

## Этап: географическое ядро

**Ключевая точка фронтенда:** `3fbef9cbdb17f13f45063b923b0ab08ec1b62471`.

Сделано:

- подключён PostGIS;
- создан нормализованный справочник географии;
- заложена иерархия страна → регион → город → административный округ → район → метро/микрорайон;
- старые текстовые поля города временно оставлены для обратной совместимости;
- добавлена синхронизация старых и новых геополей;
- каталог и Beauty начали получать единый географический контекст.

## Этап: Москва — округа и районы

- В базу добавлены все **12 административных округов Москвы**.
- Добавлены **132 района Москвы**.
- Для части районов импортированы реальные OSM-границы и центры PostGIS.
- Геометрия районов используется как фундамент будущего «Рядом со мной» и автоматического определения района.

## Этап: метро

- Импортированы станции/транспортные узлы Москвы с координатами.
- Основной источник построен на OSM/GTFS; дополнительный источник использовался для новых станций, отсутствовавших в основном наборе.
- Дубли пересадочных узлов нормализованы.
- В активном справочнике сформированы уникальные станции/узлы; среди проверенных новых станций — Вавиловская, ЗИЛ, Новомосковская.

## Этап: геопоиск и RPC

Созданы/обновлены серверные функции:

- поиск дочерних геообъектов;
- разрешение координаты в город/район/метро;
- рекурсивная проверка принадлежности территории;
- сохранение пользовательского геоконтекста;
- каталог с фильтрами по городу/территории/метро/радиусу;
- Beauty-каталог с фильтрами по городу/территории/метро/радиусу.

Радиусы поиска: **1 / 3 / 5 / 10 км** в интерфейсе; серверное ядро поддерживает более широкий допустимый диапазон.

## Этап: Нягань скрыта

- По решению владельца проекта Нягань временно исключена из публичного рынка.
- Город не удалён физически из истории/данных, а помечен неактивным/скрытым, чтобы сохранить совместимость.
- Старые пользовательские настройки Нягани мигрированы на Москву.

Изменено:

- состояние «город не выбран» убрано из пользовательского сценария;
- **Москва устанавливается немедленно при загрузке `geo-core.js`**;
- старый локальный контекст другого города принудительно переводится на Москву;
- поле поиска сразу говорит «Что ищете в Москве?»;

- кнопка больше не отвечает за выбор города — она открывает уточнение **округ → район → метро → радиус**;
- обработчик кнопки назначается самим геомодулем и переопределяет устаревшие обработчики страницы;
- авторизованный пользователь по-прежнему может сохранять уточнённый геоконтекст в Supabase.

# 9. Безопасность и технические принципы

На текущем этапе зафиксированы следующие правила архитектуры:

- публичные API возвращают только данные, предназначенные для витрины;
- приватные контакты, CRM-заметки и платёжные технические данные не выдаются anon;
- на публичных таблицах применяется RLS;
- управляющие RPC требуют авторизации;
- для `SECURITY DEFINER` фиксируется `search_path`, EXECUTE выдаётся только необходимым ролям;
- после DDL/новых функций выполняется аудит прав и Supabase Advisor;
- пользовательские изображения ограничиваются по типам и размеру;
- потенциально чувствительные данные не хранятся во frontend-коде;
- изменения географии делаются совместимо со старыми данными, пока миграция продавцов не завершена.
